Conférence Hub

Système automatisé de gestion des inscriptions, d'émission de billets QR et de contrôle d'accès pour les événements du Club Informatique.

01

Le Constat & La Solution

Le Problème : Lors des conférences universitaires, l'organisation est souvent aveugle. On lance des affiches, mais on ignore combien d'étudiants seront réellement présents, ce qui complique la logistique (chaises, packs d'eau, badges).

Ma Solution : Une plateforme d'inscription de bout en bout (Type "Eventbrite" miniature). Un QR Code sur l'affiche physique redirige vers un formulaire. L'étudiant s'inscrit, reçoit son E-Ticket par mail, et l'organisateur scanne ce ticket à l'entrée le jour J.

02

Le Flux (Workflow)

1

Acquisition

  • Scan du QR Code sur l'affiche.
  • Redirection vers la Landing Page de l'événement.
  • Lecture du programme et des intervenants.
2

Inscription

  • Formulaire épuré : Nom, Prénom, Email, Filière, Niveau.
  • Pas de mot de passe pour l'étudiant (friction zéro).
  • Enregistrement en base de données.
3

Génération & Envoi

  • Création automatique d'un ID unique.
  • Génération d'un QR Code lié à cet ID.
  • Déclenchement API Brevo : Envoi du mail avec le billet (Lieu, Heure, QR).
4

Le Jour J (Contrôle)

  • L'étudiant présente son mail à l'entrée.
  • Le staff scanne le QR avec un smartphone.
  • Le système vérifie la validité et marque l'étudiant comme "Présent".
03

Cahier des Charges Technique (Stack MERN)

Pour ce projet, je propose une architecture MERN simple, robuste et évolutive : MongoDB + Express + React + Node.js. L'objectif est d'avoir un MVP fonctionnel, facile à maintenir et capable d'évoluer vers un vrai tableau de bord événementiel.

1. Base de Données (MongoDB)

Une seule collection Attendees pour stocker les inscriptions des participants.

  • Nom, Prénom
  • Email unique pour éviter les doublons
  • Filière, Niveau pour le reporting
  • TicketID : UUID généré par le serveur
  • Status : Registered ou Attended
2. Backend Node / Express

Le serveur expose des endpoints clairs et sécurisés pour gérer l'inscription, le dashboard et le scan.

  • /api/register : réception des données, vérification de l'email, création du participant, génération du QR Code et envoi d'email via Brevo.
  • /api/admin/login : authentification des organisateurs pour générer un JWT.
  • /api/admin/attendees : lecture des inscrits pour le Dashboard.
  • /api/scan/:ticketId : route protégée pour valider le billet et marquer la présence.

Le backend applique un modèle MVC simple :

  • Models : définition du schéma MongoDB
  • Controllers : logique métier des routes
  • Routes : points d'entrée API
3. Frontend React

Une interface divisée en deux expériences : public et administrateur.

  • Public : landing page avec présentation, programme et formulaire d'inscription.
  • Validation : contrôles de saisie côté client pour éviter les erreurs de formulaire.
  • Admin : Dashboard protégé avec tableau des inscrits, compteur global et export CSV.
  • Convivialité : interface claire pour le staff, accessible depuis un smartphone ou un laptop.
04

Logique d'Accès (Le Dashboard)

Le Dashboard est réservé à l'équipe d'organisation : président du club et architecte technique. Il doit permettre de consulter la liste des inscrits, de suivre les présences et d'activer le scan des billets sans ajouter de complexité inutile.

Voici le fonctionnement proposé :

  • Connexion Admin : un administrateur se connecte via /api/admin/login avec un email et un mot de passe.
  • Stockage simple : les identifiants d'administration sont conservés dans le fichier .env du serveur plutôt que dans une collection MongoDB dédiée.
  • Token sécurisé : la connexion génère un JWT valable 12 heures.
  • Accès protégé : le front-end place le token dans un cookie HttpOnly et le transmet à chaque appel protégé.
  • Middleware de sécurité : avant d'afficher le Dashboard ou de valider un scan, le serveur vérifie le token. Sans token valide, l'accès est refusé avec une erreur 401 Unauthorized.

Cette approche reste légère pour un premier MVP, tout en garantissant :

  • un accès restreint aux pages d'administration,
  • une séparation claire entre public et privé,
  • une protection du point de contrôle de scan.

Pourquoi c'est adapté pour la première version

Il s'agit d'une sécurisation pragmatique : pas de système de rôles complet, pas de base d'administrateurs lourde. On protège seulement l'accès au Dashboard et à la route de scan avec un token valide, ce qui est suffisant pour un petit projet événementiel.
